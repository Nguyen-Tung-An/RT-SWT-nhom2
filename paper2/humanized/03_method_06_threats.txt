=== Methodology ===

-- Dataset Construction --

Our starting point is the set of ten projects: eight Java repositories ( commons-cli ,
commons-csv , commons-collections , commons-math , gson , jsoup , joda-time , jfreechart )
and two Python repositories ( flask , requests ). We measure the cyclomatic complexity of
their functions with Lizard 1.23.0, selecting medium-complexity methods (5 <= CC <= 10) as
the population pool for our sampling, matching the complexity range studied in our earlier
work.

A function's complexity on its own does not make it a good target for sampling into a test
suite: a study which samples test targets by complexity but fails to account for
testability measures two things at once, namely how effectively a particular generator can
implement tests for the targets that were selected, plus how frequently those targets could
actually be tested in the first place. We apply five additional criteria, each fixed before
any test was generated, and each justified by whether any tool at all could reach the
target through the public API (an LLM, a search-based generator, or even a human):

F1 - Non-trivial body: nloc >= 3. This excludes stubs, abstract methods, and interface
declaration from having any branches to cover.

F2 - Public/exported: Java: public ; Python: name does not start with an underscore. A
private method cannot be invoked from an external test class by default; by using
reflection, one can bypass the visibility restriction, but then the compiler no longer
checks any name in the test (see Section: Measurement: Four Tiers), so compilation ceases
to be evidence of anything.

F3 - Unambiguous name: Java: method name occurs once in the declaring class; Python:
function name occurs once in the module. An overloaded name cannot be specified in a prompt
unambiguously, and the compiler rejects the resulting call as ambiguous.

F4 - Verified declaring class: the declaring class is resolved with a brace-depth stack
that pops on block exit. Taking "the nearest enclosing class declaration" without popping
leads to assigning methods to whichever nested class was declared most recently, which is
wrong whenever the target follows a nested type in the same file.

F5 - Dynamically resolvable: (Python-specific) The module is imported, the qualified name
is walked via getattr , and the result is checked for being callable; syntactic inference
is not sufficient.

Table 1 presents the overall funnel; note that we report the number of functions surviving
each stage, and not the ones eliminated. The reason is that the attrition is of interest:
out of 1,848 functions with complexity between 5 and 10, only 474 (26 %) are public and
unambiguous, and hence can be testably targeted by an external generator. Overall,
testability considerations rule out roughly three quarters of the medium-complexity

Out of the surviving pool (Java 406, Python 64), we sampled 60 Java and 60 Python functions
as test targets. We distributed the targets between the repos in the pool as broadly as
possible (Java: between 3-9 functions per repo; Python: 32 functions in requests , 28 in
flask ). The complexity was skewed toward the lower end of the band (CC=5: 56 functions;
CC >=8: 23), with a median line count of 17. Out of the Python targets, 34 were instance
methods and 26 were module functions; all 120 targets were verified to be dynamically
resolvable at run-time before testing commenced. One Java target was later found to violate
F2 — our own parser had recorded a protected method as public — and is excluded, so Java
results are reported over n = 59 and Python over n = 60 (see Threats to Validity).

-- Test Generation --

All tests were generated by `gpt-4o-mini-2024-07-18` , temperature = 0, top_p = 1.0,
max_tokens = 2048, as a single API call per function with no feedback loop or retrieval.

We evaluated two variations of the one-shot prompt, each of which included one worked
example (add function and test). Both variations are one-shot in the traditional sense but
differ in one detail:

V1 - baseline: the target function is named and shown in the prompt. This is the variation
used in our previous study.

V2 - target-specified: same as V1 but with an additional block before the task description
giving the fully qualified target name, signature, declaring class, and, for instance
methods, an executed constructor call that has been verified to produce the receiver.

The choice to retain the worked example in both variations was not accidental: an early
draft of the enriched prompt omitted it, thus differing from V1 in two respects (no example
+ additional metadata), making it impossible to isolate the effect of the metadata. We
report that variation only as a secondary observation and label it zero-shot, as it
technically is one.

-- Measurement: Four Tiers --

A simple binary metric would conflate various flavors of failure, so we report four tiers
of success for each generated test suite. Each subsequent tier is strictly more stringent
than the previous, and the first two can be achieved by a test suite that does not actually
test anything.

T1 - Compiles/collects: the test file parses and type-checks.

T2 - At least one green test: at least one test in the suite passes when executed against
the unmodified source.

T3 - Reaches the target: achieves branch coverage > 0 within the target's line range
[start, end].

T4 - Detects faults: has a mutation score > 0 within the same range.

Only the tests at T4 confirm that a suite actually tests what it claims to; we report all
four tiers nevertheless, as T1-T2 can be achieved by a suite that does not test anything.

T1 can be achieved by a suite that uses reflection: reflection turns every name into a
string, so the compiler stops checking it, and a call to
getDeclaredMethod("aNameThatDoesNotExist") compiles with return code 0 and fails only at
run-time. Any compilation-based validity rate is therefore uninformative for suites that
use reflection.

T2 can be achieved by an assertion-free suite: the search-based suite generated for
requests.hooks (target dispatch_hook ) contains exactly one test, and that test is a single
bare call to a different function in the same module, with no assertion of any kind. It
compiles, it collects, and it passes — T1 and T2 are both satisfied — while measured branch
coverage inside the target's line range is 0. A green-test criterion records this as a
success.

Branch coverage is measured with coverage.py (Python) and by executing the generated JUnit
suites through the JUnit Platform launcher (Java); in both cases we attribute the coverage
to the target's line range rather than to the whole file. Mutation analysis uses the same
set of operators for both languages: arithmetic (+ and -, x and /), relational (>/>=,
</<=), equality (= =/!=), boolean (AND/OR), boolean constant inversion, and numeric
constant increment, with a maximum of 20 mutants per function, restricted to the target's
line range.

Two implementation details deserve special attention as they may bias the results:

Mutation requires overwriting the source, so mutants are applied to an isolated copy of the
source tree placed before the original on the import path; run directly on a shared tree,
mutation silently corrupts any concurrent measurement reading that tree.

JUnit~5 Jupiter~5.x works with JUnit Platform~1.x; a Jupiter~6 artifact in the same
classpath will cause the launcher to report 0 tests found while exiting with code 0, thus
faking an empty suite.

-- Baselines --

Each baseline was run per class (Java) or per module (Python), as appropriate for the tool,
and results were attributed to individual functions by line range, as with the LLM suites.

EvoSuite 1.2.0: 60 s per class, under JDK~11. EvoSuite uses deep reflection to explore
internal JDK classes, which the module system blocks from Java~9 onward; the master process
spawns its client under JAVA_HOME , so these need to agree, or the client will fail to
launch while the master exits successfully. Since the projects were compiled with JDK~17,
we recompiled sources to Java~11 bytecode in a separate directory to evaluate EvoSuite,
leaving the original build intact.

Randoop 4.3.3: 60 s per class, JDK~17.

Pynguin 0.45.0: 90 s per module; evaluated in two configurations reported side-by-side. In
its default configuration, Pynguin serializes module state for a worker process with dill
and exits immediately if a C-type extension object cannot be found by name, reporting no
tests for several modules. We also report results from disabling the master-worker split in
Pynguin, as it separates "the tool scored poorly" from "the tool did not run at all".

-- Statistical Analysis --

We applied the paired Wilcoxon signed-rank test with rank-biserial correlation as the
effect size and alpha = 0.05; Java and Python were analyzed separately throughout, because
the toolchains differ and because Java enforces access control while Python does not, with
every rate reported over the 60 functions of its own language.

The results are reported at two levels: all (n = 60 per language; unmeasured values are
considered 0) and effective (the subset with a non-zero value), the latter often
substantially higher than the former. Both levels are reported in parallel, and the all
level is reported even where the effective level is more favourable.

Every detail of the design was specified in a pre-registration before baseline evaluations
began, including the criteria, the tools, the budgets, the two-branch analysis of Pynguin,
and the hypotheses.

=== Threats to Validity ===

-- Construct Validity --

[What a validity flag measures.]

The single largest threat to construct validity in this study stems from the usual "valid
suite" indicator not measuring what its name suggests, and failing silently when it does
not, with multiple ways to obtain a suite that parses and collects but does not actually
test anything; we observe six such cases, four of which are present in our instrumentation.

A compilation flag obtained via a coverage report only confirms the presence of a class
under test; coverage tools track all classes in a project, including those not loaded, and
such a class will report 0% branch coverage, which the parser treats as a valid, compilable
function with 0% coverage.

"The suite has at least one test that executed" considers a file with all tests failed as
valid.

Reflection makes name resolution dynamic, so the compiler can no longer check the names it
resolves, and any compilation-based rate becomes uninformative for a suite that uses it.
Finally, a test launcher can report 0 tests found while exiting with code 0, thus falsely
recording an empty suite as successful if the version of the launcher does not match the
version of the test framework.

[MOI - CAN HUMANIZE] The fifth case is worth stating in full, because believing it would
have inverted a published conclusion. Our Java runner and the generated tests were compiled
with the default JDK (class file version 61) and executed under the JDK 11 required by
EvoSuite, which reads at most version 55. The resulting UnsupportedClassVersionError was
raised inside a child process, so the harness saw only the absence of a result line and
recorded "no tests ran" for every target. EvoSuite scored 0/60, and a paired test against
it returned p = 0.005 with a rank-biserial correlation of -1.000. Had we reported it, the
paper would have claimed a statistically significant advantage for the model over EvoSuite.
A well-formed p-value made the artefact look more credible, not less.

[MOI - CAN HUMANIZE] The sixth case concerns the green-test gate itself. Our Python
implementation retained the passing tests and discarded the failing ones, as T2 specifies;
our Java implementation rejected the entire function if any single test failed. The two
languages were measuring different constructs under one name, and the Java side
contradicted the definition we had registered in advance. We corrected it and report both
settings throughout; the correction is discussed under conclusion validity below, because
it moves results in our own favour.

None of these represent an exceptional condition; each returns a plausible number. We
report all four tiers of measurement, and only consider T4 ("mutation detected within the
target's line range") to be evidence that a suite actually tests what it claims to.

[Mutation operators.]

Our operator set is deliberately minimal and identical for both languages, which makes the
two comparable; it includes fewer operators than a production mutation framework would, so
absolute mutation scores are not comparable with studies using PIT or `mutmut` , and only
within-study comparisons are meaningful. We also limit the number of mutants to 20 per
function, which reduces the resolution of the metric for larger functions.

-- Internal Validity --

[Sampling.]

One Java target was incorrectly classified as public by our miner: LocalTime.getField is
marked protected , but the parser matched it against a same-name declaration in a nested
class and incorrectly recorded it as public, passing the public-only filter. Upon
inspection of the real declaration line, this was the only occurrence among 60 Java
targets; we exclude it from further consideration. We report it here because it is
precisely the class-attribution error this study is about, reproduced in our own tooling —
knowing about a failure mode does not confer immunity to it.

[Concurrency.]

When measuring mutation score, source files are overwritten; running mutation directly on a
shared source tree corrupts any concurrent measurement reading that tree, silently. We
mutate an isolated copy of the source tree placed before the original on the import path
and verify that the original tree was not modified after each measurement.

-- External Validity --

[Source exhaustion in Python.]

After applying testability criteria, only 64 Python functions in the two projects are
viable for testing, of which 34 were already present in our previous data set; a strictly
held-out replication therefore has roughly 30 Python functions to work with, unless new
repositories are added. Our Python sample is also drawn from two web-oriented libraries and
may not generalise to other domains.

[Complexity distribution.]

While we sampled functions from the medium complexity band (5 <= CC <= 10), the
distribution was not uniform, and more functions fell towards the lower end (CC = 5: 56 of
120 functions); observations from the upper half of the band are underrepresented.

[Model and configuration.]

All tests were performed with one model at one temperature; we make no claims about
performance with other models and configurations, and the deterministic setting means we do
not estimate run-to-run variance.

-- Conclusion Validity --

[Baseline configuration.]

Three issues pertain to the configuration of the baseline test generators. When running
EvoSuite, we used a classpath that contained only the module's own compiled classes: using
the full dependency classpath would cause its bytecode reader to abort in a way that
produces no output while reporting success, and we were unable to identify the offending
artifact. EvoSuite may therefore be performing below its usual capabilities in this
configuration. Additionally, seven Java targets in one multi-module project could not be
recompiled to Java~11 bytecode and fall outside EvoSuite's coverage; finally, our Randoop
version differs from the one used in our previous evaluation, and results should be
compared within this study only.

[Pre-registration and two deviations.]

The hypotheses, questions, tools, budget, and two-branch analysis of Pynguin were committed
to a public repository before any baseline was evaluated.

The first deviation was that the enriched prompt we intended to use was discovered to omit
the worked example, rendering it zero-shot rather than one-shot and differing from the
baseline in two respects. We added a prompt condition that retains the worked example while
varying the target specification, noted this change in the pre-registration with a
timestamp, and left the original hypothesis untouched; the zero-shot variant is only
reported as a secondary observation.

[MOI - CAN HUMANIZE] The second deviation changed the instrument after results had been
seen, and changed it in a direction favourable to us, so we state it plainly. The Java
green-test gate described above was corrected to match the registered definition of T2.
Eight functions under the baseline prompt and ten under the target-specified prompt were
affected, against two for each of the two Java baselines, so the correction helps the model
more than it helps its competitors. Three safeguards apply. The pre-correction results were
written to the repository and committed before the corrected measurement was run, so the
timestamps preclude selecting between them afterwards. Both settings are reported side by
side for every Java comparison. And we state no conclusion that does not hold under both;
where the two disagree, we report the comparison as inconclusive. The Python measurements
were not re-run, having matched the registered definition from the start.
