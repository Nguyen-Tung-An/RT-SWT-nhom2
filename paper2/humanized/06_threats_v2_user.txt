-- Construct Validity --

[What a validity flag measures.]

The primary construct validity threat in this domain relates to validity flags: the
proposed "valid suite" metric is not a valid measure of the construct it claims to measure.
We observed six cases overall, four of which relate to our own instrumentation:

1. A compilation flag inferred from a coverage report only checks whether the class is
present in it, whether it was actually loaded or not. Coverage reporters usually list all
classes in a project, including those not actually loaded; those report 0% branch coverage,
which the parser treats as a successfully compiled function with 0% coverage.

2. Criteria such as "at least one test executed" count a file where every test failed as
having executed successfully.

3. Reflection makes name checking impossible, rendering any compilation-based rate
irrelevant for a suite that uses it. Separately, a version mismatch between the tools can
make a test launcher report zero tests found and still exit successfully.

4. The fifth case had particularly instructive consequences. Our Java runner and the
generated tests were compiled with the default JDK (class file version 61) but executed
under the JDK 11 that EvoSuite requires, which reads at most version 55. The resulting
UnsupportedClassVersionError was raised inside a child process, so the harness only saw the
absence of a result line and recorded "no tests ran" for every target. EvoSuite scored
0/60, and a paired test against it returned p = 0.005 with a rank-biserial correlation of
-1.000. Had we trusted that number, the paper would have claimed a statistically
significant advantage for the model over EvoSuite; a well-formed p-value made the artefact
look more credible, not less.

The sixth validity flag threat is the green-test gate. Our Python implementation kept the
passing tests and discarded the failing ones, as T2 describes; the Java implementation used
in Section (Results) discarded the whole function if any test in it had failed. The two
languages were measured against different constructs under the same name, and the Java side
contradicted the definition we had registered for T2. We fixed the implementation and
report both settings throughout the results; the Java-side fix is discussed below under
conclusion validity, as a beneficial surprise.

Overall, none of the six threats produces an outright error; each merely returns a
plausible value. We therefore report the four nested tiers of Section (Measurement: Four
Tiers) rather than a single flag, and only consider T4 (fault detection within the target's
line range) as measuring progress toward a valid suite.

[Mutation operators.]

Our operator set is deliberately reduced and identical for the two languages, to measure
them against a common reference. It has less expressive power than a production mutation
testing framework, and absolute scores cannot be directly compared to the literature using
PIT or `mutmut`; mutation-score comparisons are only made within this work. We also cap the
number of mutants at 20 per function, which reduces the resolution of the score for larger
functions.

-- Internal Validity --

[Sampling.]

One Java target, `LocalTime.getField`, had its accessibility incorrectly parsed by our
miner. The function is declared `protected`, but the parser matched a same-name declaration
in a nested class and recorded it as public, passing the public-only filter. Upon
inspection of the real declaration line, this was found to be the only occurrence among the
60 Java functions; this function is excluded from the analysis. We report the case here
because it is precisely the class-attribution error this study is about, reproduced in our
own miner. Knowing about a failure mode does not make one immune to it.

[Concurrency.]

Mutation analysis runs by overwriting source files. Concurrent execution of such runs on a
shared source tree corrupts the other analyses, with no visible clues. We always mutate an
isolated copy placed ahead of the main source tree on the import path, and verify that the
original tree's files are not modified after each run.

-- External Validity --

[Source exhaustion in Python.]

Out of the two Python projects, only 64 Python functions met all testability criteria. Of
these, 34 already appear in the earlier dataset; a strictly held-out reproduction from these
two projects is limited to about 30 functions, unless additional repositories are added.

[Complexity distribution.]

The sample distribution for cyclomatic complexity is skewed towards the lower edge of the
selected band, with 56 out of 120 functions having a CC of 5. Predictions about the upper
half of the band may have less supporting evidence.

[Model and configuration.]

A single model at a single temperature was used; we make no claims about applicability to
other models, or even to other configurations of this same model. The deterministic setting
makes no room for estimation of variance across runs.

-- Conclusion Validity --

[Baseline configuration.]

Three factors limit the conclusions about the baseline comparison. EvoSuite was run with a
classpath containing only the module's own classes; with the full dependency classpath its
bytecode reader aborts in a way that produces no output while still reporting success, and
we were unable to identify the specific artifact causing the failure. EvoSuite's baseline
may therefore be lower than it would be in a fully configured environment. Seven Java
functions in one multi-module project could not be recompiled to Java 11 bytecode and thus
fall outside EvoSuite's coverage. Finally, our Randoop version differs from the one used in
the earlier study; comparisons to it are only made within the confines of this study.

[Pre-registration and two deviations.]

Research questions, hypotheses, tool versions, budgets, and the two-branch Pynguin design
were committed to the pre-registration before any baseline was evaluated.

The first deviation added an extra condition. Upon inspection, the enriched prompt we had
intended to use did not actually contain the worked example, making it a zero-shot prompt
rather than a one-shot one, and thus differing from the baseline in two respects at once:
it dropped the worked example and it added the target metadata. We added a corrected
condition that keeps the worked example and varies only the target specification, noted this
change in the updated pre-registration along with its date, and left the original hypothesis
untouched. The uncorrected prompt is still reported in the results only as a secondary
observation.

The second deviation involved a change to the instrumentation after observing preliminary
results; the change favored the model, which is why it is explicitly called out. The Java
green-test gate described earlier was adjusted to conform to the pre-registered definition
of T2. Eight functions were affected under the baseline prompt and ten under the
target-specified prompt, versus two functions for each of the two Java baselines; overall
the correction helped the model more than it helped its competitors. Three safeguards are in
place. The pre-correction runs were written to the repository and committed before the
corrected measurement was run, so their timestamps preclude selecting between the two
afterwards. Both settings are always reported for the Java comparisons, and no conclusion is
drawn that would not be supported under both. The Python measurements were not re-run, as
they already matched the registered definition of T2 from the start.
