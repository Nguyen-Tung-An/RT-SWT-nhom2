# Measurement Journal — How the Second Study Was Measured

A detailed record of the measurement work for the clean-dataset study: the exact tools and
versions, how each of the four tiers was measured, which script produced which number, and a
step-by-step chronology of the runs from 23–24 July. Every reported figure traces to
`ms-analysis/RESULTS-clean.md` (generated by `report_clean.py` straight from CSV).

---

| Tool | Version | Role in this study |
|---|---|---|

| EvoSuite | 1.2.0 (`tools/evosuite-1.2.0.jar`) | Search-based baseline (Java), 60 s/class |

| Pynguin | 0.45.0 | Search-based baseline (Python), 90 s/module |

| `mutation_java.py` / `mutation_on_target.py` | custom | T4 mutation-on-target harness |

**Why a custom mutation harness instead of PIT / JaCoCo.** The first study's numbers were
produced with PIT and JaCoCo, and those numbers were exactly what we were re-checking. To
avoid re-using the infrastructure under suspicion, T4 was measured with a small,
auditable harness that mutates only the target's line range and counts a mutant killed only
when a test that was green on the original source fails on the mutant. It also runs on an
isolated copy of the source tree, so concurrent measurements never read a mutated file.

## 2. How each tier was measured

The pipeline is four nested tiers. Each tier was measured by a specific tool and script; the
numbers land in per-condition CSVs under `ms-analysis/results/`.

**Sampling (before any tier).** `mine_clean.py` runs Lizard to get cyclomatic complexity,
keeps the band 5 ≤ CC ≤ 10, then applies F1–F5 (non-trivial body, public/exported,
unambiguous name, verified declaring class via a brace-depth stack, dynamically resolvable
for Python). The funnel: **1,848 → 753 (F3) → 474 (F2) → 64 (F5, Python)**; final pool Java
406, Python 64; sampled 60 + 60. `DATA-STANDARDS.md` documents each criterion.

**Generation.** `run_experiment_v3fair.py` calls `gpt-4o-mini-2024-07-18` once per function,
no feedback loop, no retrieval. Two one-shot prompts (V1 baseline, V2 target-specified) differ
in exactly one block. Suites are written to `generated_tests/clean_v1/` and
`generated_tests/clean_v3fair/`.

**T1 — Compiles / collects.** Java: `javac` under JDK 17. Python: `pytest` collection. A file
that does not compile or collect fails T1.

**T2 — At least one green test.** Java: `JUnitRunner` prints one `GREEN <method>` line per
passing test; the harness keeps those and drops the failing ones (per-test, matching the
pre-registered T2). Python: `greencheck.py` does the same via pytest node IDs. This per-test
gate is the one whose Java implementation was found wrong and corrected (see §3, 23:29).

**T3 — Reaches the target.** `coverage.py` branch coverage restricted to the target's line
range `[start, end]`. Reported **for Python only**; the Java pipeline runs suites through the
JUnit Platform launcher and rests on T4, so no Java branch-coverage figure is claimed.

**T4 — Detects faults.** `mutation_on_target.py` (Python) and `mutation_java.py` (Java):
mutate a copy of the source, one operator per site, within the target's line range; a mutant
is killed only when a previously green test now fails. Operator set is identical across
languages (arithmetic, relational, equality, boolean, boolean-constant, numeric-increment).
Cap: 20 mutants per Java function, 30 per Python function — it binds only CJ-004 and CJ-026
(Java) and no Python function, so it affects score resolution, not tier outcome.

**Baselines.** `run_baseline_java.py` generates EvoSuite (JDK 11, on Java-11 bytecode built by
`build_jdk11_classes.py`) and Randoop (JDK 17); `measure_pynguin.py` runs Pynguin in two
configurations (default, and master–worker split disabled). All three are then scored through
the **same four-tier harness** as the LLM suites (`measure_baseline.py`), attributing results
to individual functions by line range.

**Statistics.** `analyze_clean.py` runs paired Wilcoxon signed-rank tests (matched on function
id, α = 0.05, matched-pairs rank-biserial). `report_clean.py` assembles `RESULTS-clean.md`
from the CSVs — no number is typed by hand.

## 3. Chronology of the runs (23–24 July)

### 23 July

- **18:24** — Clean dataset mined (`mine_clean.py`). Funnel 1,848 → 474; pool Java 406,
  Python 64; 60 + 60 sampled.
- **19:47** — Pre-registration committed (`PREREGISTRATION-clean.md`), **before any baseline
  ran**: RQs, hypotheses (H-B predicts the enriched prompt is *not* better), and locked
  baseline configs (Pynguin 90 s/module × 2 configs; EvoSuite 60 s/class JDK 11; Randoop
  60 s/class JDK 17).
- **21:19** — v3-fair prompt built (`run_experiment_v3fair.py`), fixing an earlier confound
  where the enriched prompt had accidentally become zero-shot.
- **22:45** — Randoop T4 baseline measured; first Wilcoxon test against it.
- **23:15** — **Sixth measurement defect found.** The Java runner and tests were compiled
  under JDK 17 (class version 61) but run under JDK 11 (reads ≤ 55). The
  `UnsupportedClassVersionError` was thrown inside a child process, so the harness recorded
  "no tests ran" for every target. EvoSuite scored a false **0/60**; a paired test against
  that turned it into **p = 0.005, rank-biserial −1.000** — a significant claim in the wrong
  direction.
- **23:19** — Retracted a wrong self-diagnosis: Randoop's 18/60 was *not* affected (it uses
  one JDK throughout); its number stood.
- **23:25** — EvoSuite re-measured with all three JDK sites fixed: **24/60**.
- **23:29** — **Green-gate asymmetry found and corrected.** Python filtered green tests
  per-test (correct, per T2); Java rejected the whole function if any test failed. The
  pre-correction numbers were saved to `*_strictgate.csv` and committed **first**, both gates
  are reported side by side, and no conclusion is stated unless it holds under both
  (amendment 4bis).
- **23:29** — Pynguin measured, both configs: **2/60** each. Disabling the master–worker split
  reduced no-suite from 39 to 35, but of 17 newly generated suites 14 failed at collection, so
  T4 was unchanged.
- **23:37** — `report_clean.py` added; `RESULTS-clean.md` now generated from CSV.

### 24 July

- **~01:00** — Randoop re-measured under the per-test gate: **19/59** (whole-suite 18/59).
  All four Java baseline numbers finalized: EvoSuite 23/24, Randoop 19/18, GPT 16/10.
- Remainder — paper writing and adversarial verification of every number against the CSVs
  (see `WORK-LOG.md`).

## 5. Regenerate everything

```bash
# rebuild the consolidated results table from the CSVs
python ms-analysis/scripts/report_clean.py

# re-run the statistical tests
python ms-analysis/scripts/analyze_clean.py
```

Environment overrides used during measurement: `MJ_GT` / `MT_GT` / `BL_GT` point the Java,
Python, and baseline harnesses at `data/clean_v3.csv`; `MJ_GATE=pertest|strict` selects the
green gate.
